PROTOCOL · 傳輸格式與可靠性
一則訊息就是一顆球
SIGN → RELAY → UNITY · type: ball
{
  "type": "ball",
  "id": "b_20261005_021850_qtmy",
  "colorId": 7,
  "color": "#8258C2",
  "signature": "data:image/png;base64,…",
  "createdAt": "2026-10-05T02:18:50+08:00"
}
其他訊息
{ "type": "hello", "role": "sign" | "unity" }   連線後先註冊
{ "type": "ack", "id": "b_…" }               中繼 → 簽名端
連線ws://<投影主機>:8787/ws，先送 hello 註冊是簽名端還是 Unity
顏色同時帶色號與色值：Unity 直接用色值上色，之後改色盤只要改網頁
簽名512×512 透明 PNG、白色筆跡，實測一顆約 15 KB；涵蓋整顆球的直徑，正投影貼在球正面
確認中繼收到就回 ack；收到前球存在瀏覽器（localStorage），重新整理也不會掉
去重id＝日期＋時間＋亂數；重送時中繼與 Unity 都依 id 略過重複
斷線每 15 秒心跳；兩端都會自動重連（0.5–5 秒退避）
與規格書不同

規格書 v0.5 寫的是 MQTT；本次依實作改用 Node.js WebSocket。雕塑燈控（ESP32）要沿用 WebSocket 或另開 MQTT，待確認。

NETWORK · 內網設定
IP 與連線埠規劃 建議
裝置IP連線埠／服務說明
路由器192.168.10.1—DHCP（保留位址）不接外網；關閉 Wi-Fi，或只留給維護用的隱藏 SSID
投影主機192.168.10.10有線8787 TCP · HTTP＋WebSocket跑 Node.js 中繼與 Unity；Windows 防火牆開放 8787 入站
簽名端 mini PC192.168.10.21有線瀏覽器 → 主機 :8787開機自動以 Chrome 全螢幕開啟 http://192.168.10.10:8787/sign/?full&ws
燈光控制器 ESP32192.168.10.30有線待確認建議乙太網路版；協定沿用 WebSocket 或改 MQTT 待定
維護筆電DHCP有線（臨時）—現場除錯用，不常駐
開機順序（建議）

路由器 → 投影主機（Node 中繼 → Unity）→ 簽名端。順序錯了也不會掉球：簽名端會排隊重送，中繼也會等 Unity 連上再補送。

為什麼要封閉內網

中繼不需要上網；不接外網能避開展場 Wi-Fi 干擾與外部連線，也省掉帳號密碼外洩的風險。需要遠端維護時再臨時接線。
